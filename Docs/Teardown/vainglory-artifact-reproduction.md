# Vainglory 4.13 artifact research

Independent reproduction performed 2026-07-31 from the preserved APK and
Windows content store. This is the artifact-level evidence leaf. It does not
replace the product/visual audit and it does not claim that a historical online
service still works.

## Evidence labels

- **Observed** — read directly from a named local artifact.
- **Reproduced** — regenerated by the command or repository tool named here.
- **Inferred** — best explanation still compatible with alternatives.
- **Inherited/unverified** — present in an earlier report but not backed by a
  preserved raw capture that this pass could replay.

The proprietary inputs stay outside the repository under `D:/Downloads/vg`.
Only hashes, small structural facts and original inspection tools are retained.
The unsigned archived Windows executable was not launched.

Tool requirements and the two safe rerun commands are indexed in
[Tools/Teardown/README.md](../../Tools/Teardown/README.md).

## 2. Plaintext before binary

The 128-byte `assets/Data/Startup.ini` contains the bootstrap route
`http://preauth.superevilmegacorp.net/kindred/live/[REVISION]-status-redirect`.
This was found before inspecting native code.

A single low-impact request on 2026-07-31 returned HTTP 200 and the 25-byte
redirect value `rpc.kindred-live.net:443`. This proves that route answered that
request at that time. It does not prove login, matchmaking or a playable
backend.

## 3. Native feasibility test: stop before Ghidra

Android NDK LLVM tools reproduced the arm64 ELF measurements:

| Section/property | Result |
|---|---:|
| ELF type | AArch64 shared object |
| sections | 25 |
| `.text` | 19,877,380 bytes |
| `.rodata` | 3,002,493 bytes |
| `.dynstr` | 191,107 bytes |
| `.symtab` | absent |
| printable strings, minimum 8 bytes | 31,661 |
| JNI symbols | 36 |

JNI exports include the Nuo application startup and touch-event boundary, so
Java is a shell around a native engine. Old SEMC/game hostnames occur as native
strings; `kindred-live.net` does not, which is consistent with runtime
bootstrap assignment.

`llvm-nm --dynamic` produced 6,718 lines and 532 unique `_ZT[IVS]` names. After
filtering standard-library and ABI forms, eight candidates remained; inspection
showed only built-in/`std::__ndk1` type records and thunks, not game classes.
The older count of 390 used a different extraction/counting method. The useful,
tool-independent conclusion is unchanged: there is no game RTTI/class-name
anchor and no static symbol table.

Competing explanation retained: stripped code can still be reversed from call
patterns and data references. It is merely a much more expensive route. Since
the current Veilbound questions were answered by text, smali and container
metadata, opening a disassembler could not justify its cost.

```powershell
llvm-readelf.exe --sections libGameKindred.so
llvm-nm.exe --dynamic libGameKindred.so
llvm-strings.exe --bytes=8 libGameKindred.so
```

## 4. Android installer chain — corrected reproduction

A fresh decode used `apktool 3.0.3 d -r -f`; the five critical smali files
matched the previously decoded tree byte-for-byte by SHA-256. Raw resource
values reproduced:

```text
bool/DIST             = false
bool/INSTALL_ASSETS   = true
string/storefront     = GOOGLE
```

The significant call chain is:

```text
NuoBuildConfiguration.<clinit> starts STOREFRONT at NONE
  -> startup() reads resources and changes runtime STOREFRONT to GOOGLE
  -> ENABLE_GOOGLE_DOWNLOAD = (GOOGLE && DIST) = false
  -> license Checker returns true unconditionally
  -> APK asset size rounds to 0 MiB and no OBB is present
  -> tryDownloadAssets()
  -> GOOGLE branch calls mExpansionDownloader.BeginDownload()
  -> downloader was never constructed because ENABLE_GOOGLE_DOWNLOAD is false
  -> exception is caught; installer finishes
```

`TRUE_STOREFRONT = NONE` is a different field. The previous teardown conflated
it with the runtime `STOREFRONT` and therefore predicted the non-Google
missing-assets dialog. For this exact APK, that prediction is wrong.

The license hypothesis is rejected by the unconditional-success checker. The
high-level missing-data diagnosis survives: the APK contains no usable payload,
the OBB is absent and the only downloader path is disabled by this build's
resource combination. Static analysis predicts the null-downloader path; it
does not prove the exact user-visible exit timing on every Android version.

The captures are not per-UID, so “no Vainglory hostname observed” is narrower

fully unattended clean run disproved it is therefore withdrawn.

An earlier report lists four Windows client sockets. No raw socket snapshot was
preserved and no already-running process existed, so this pass labels those
addresses **inherited/unverified** instead of presenting them as reproduced
dynamic evidence.

## 6. Windows content store and container grammar

The extracted `Data/` directory contains 48,222 files totalling 3,498,231,637
bytes; 48,194 have hash-like names. The deterministic repository inspector
reproduced the following across the whole store, not a hand-picked sample:

| Check | Result |
|---|---:|
| `RSC0` files | 18,136 |
| both RSC0 size words equal `file_size - 32` | 18,136 / 18,136 |
| `CFF0` containers | 17,927 |
| declared CFF size equals whole file size | 17,927 / 17,927 |
| chunk walk reaches EOF when size includes its 8-byte header | 17,927 / 17,927 |

Of the CFF containers, 16,985 are inside RSC0 payloads and 942 are standalone.
The important parser trap is therefore independently reproduced: CFF chunk
size includes the chunk's own eight-byte header.

Run it with:

```powershell
python Tools\Teardown\inspect_vainglory_store.py `
  'D:\Downloads\vg\pc\Vainglory 4.13\Vainglory\Data'
```

Root counts are Environment 746, Characters 453, UI 28, Models 13,

## 8. Entropy boundary and bounded codec probe

The selected manifest container is
`C4/C41CC38B5CEADF09048A3750D045E47B`, 55,712 bytes, SHA-256
`20e1b351802a6cbc77ce1237c4745f4c54fa9ca6cc0601330b62e5c3474a2e6a`.
Using Shannon entropy over each payload only, excluding the eight-byte chunk
header, its first revision is:

| Tag | Chunk size including header | Payload entropy, bits/byte |
|---|---:|---:|
| `DEF0` | 16 | 2.75000 |
| `INST` | 19,184 | 7.98844 |
| `PTCH` | 6,480 | 4.47654 |
| `SYMB` | 32 | 3.77206 |

The second `INST` is 7.99271 and its adjacent `PTCH` is 4.41505. Older rounded
values of 7.96/4.31 were not reproduced because their byte range/formula was not
recorded.

`probe_vainglory_codecs.py` tested the first 19,176-byte INST payload at offsets
0, 4, 8, 12 and 16 using zlib, raw deflate, LZMA-auto, bzip2, three bounded LZ4
block output sizes, LZ4 frame and Zstandard. All 45 attempts failed. The probe is
bounded to avoid untrusted decompression output.

```powershell
python Tools\Teardown\probe_vainglory_codecs.py `
  'D:\Downloads\vg\pc\Vainglory 4.13\Vainglory\Data\C4\C41CC38B5CEADF09048A3750D045E47B'
```

This rejects those common framing/offset combinations. It does not prove a
cipher. Per-chunk encryption is the strongest current hypothesis because a
near-max-entropy `INST` sits beside a much lower-entropy structural table, but
custom compression or another transform remains possible. Identifying which
would require the stripped loader and would not change a current Veilbound
decision, so the avenue stops here.

## 9. Current public infrastructure, kept separate

At 2026-07-31T15:04Z, the public CertSpotter query returned seven unique names:
RPC, static content and five regional game-server names. Google Public DNS
returned an authenticated A record for all seven. These checks can be rerun at
the primary endpoints:

- `https://api.certspotter.com/v1/issuances?domain=kindred-live.net&include_subdomains=true&expand=dns_names`
- `https://dns.google/resolve?name=rpc.kindred-live.net&type=A`

Certificate issuance means a name appeared on a certificate. DNS means a name
currently routes. The bootstrap HTTP response means one route answered. None of
those observations entails a functioning login or game service; automated
certificate renewal is also compatible with abandoned application logic.

## 11. What transfers to Veilbound

1. **Interaction evidence:** distinct ally/enemy pretarget assets support a
   separate “candidate before commitment” state. Veilbound's release timing and
   arbitration contract remain our own design and must be proven in Unity.
2. **Rendering evidence:** indicator families are authored as parameterised
   shader-driven states. That supports a semantic visual grammar, not copying
   their shapes, colours, shader code or names.
3. **Production evidence:** a mature mobile game uses content-addressed stores,
   atlases, templates and LOD/material variants. Veilbound should use its
   prepared image/3D/Blender tools to create original assets with provenance,
   then optimize and judge them at the gameplay camera.
4. **Investigation rule:** ask the cheapest falsifiable question first and keep
   observed, inferred and inherited evidence separate. A compatible fact is not
   confirmation until competing explanations are tested.

This reproduction changed documentation and original analysis tooling only. It
made no Unity gameplay, scene or asset change.
